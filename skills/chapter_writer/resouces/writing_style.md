# 教材寫作規範（Writing Style Guide）

本文件定義本專案所有教材的寫作規範。
所有教材、講義、章節內容與課程文件，除非使用者另有要求，均應遵循本規範。
本文件的目的不是限制寫作自由，而是確保不同章節、不同課程以及不同作者所撰寫的教材，能夠維持一致的閱讀體驗與專業品質。

---

# 一、整體寫作風格

所有教材應採用平實、親切、簡單明瞭、不過份輕浮的語氣表達，
並以「大學教材」或「專業專書」作為寫作目標。
但避免聊天式回答、口語化表達、投影片式排版，以及社群媒體文章常見的寫作方式。
教材應讓學生具有閱讀一本書，而不是閱讀 PowerPoint 或 ChatGPT 對話紀錄的感受。
因此，每一個概念都應完整說明，而不是僅提供結論。

---

# 二、段落組織

每一個段落應圍繞一個主要概念。
段落內應先介紹概念，再進一步說明原因、背景或應用，最後自然銜接下一段。
請避免：
- 一句形成一個段落
- 一個概念被切割成許多短句
- 每一句都換行
- 過多留白
如果一個概念需要較長的說明，應維持在同一個段落中，而不是拆成數個零碎的小段。

---

# 三、章節安排

教材應具有清楚的階層。
建議使用：

```text
# 章
## 節
### 小節
```

不要直接跳過標題層級。
例如：
```text
#
###
```
屬於不建議的寫法。

若沒有足夠內容，不必建立新的小節。
---

# 四、概念介紹方式

介紹新的知識時，建議採用下列順序：

1. 問題或背景
2. 概念定義
3. 運作原理
4. 實際案例
5. 與其他概念的比較
6. 小結

不要一開始便直接給出定義。
應先建立學生理解問題的情境，再介紹概念。

---

# 五、專有名詞

重要專有名詞第一次出現時，請同時提供中文與英文名稱及簡稱。

例如：

> 上下文工程（Context Engineering）

> 檢索增強生成（Retrieval-Augmented Generation，RAG）

之後即可直接使用中文或英文簡稱其中之一。

整份教材應保持一致。

不要同時混用：

- 長期記憶
- Long Memory
- Persistent Memory

除非刻意比較不同名詞。

---

# 六、程式碼說明

教材中的程式碼，不應直接貼上。

每一段程式碼之前，都應說明：

- 為什麼需要這段程式？
- 它解決什麼問題？

程式碼之後，再解釋：

- 哪些部分最重要？
- 哪些地方值得注意？

不要假設讀者能夠自行理解程式。

---

# 七、圖片與流程圖

若教材包含圖片、流程圖或架構圖，不應直接引用圖片。

應先介紹：

- 為什麼需要這張圖？
- 希望讀者觀察什麼？

圖片之後，再說明：

- 圖中各元件代表什麼？
- 圖片如何對應本章內容？

避免：

> 如下圖。

而應寫成：

> 圖 3-1 展示了 Context Engineering 的主要架構。從圖中可以觀察到……

### 圖表產製與 PNG 格式規範（禁用 Mermaid 語法）

1. **全面改用清晰易讀的 PNG 圖片檔案：** 講義中的所有流程圖、架構圖、拓撲圖與概念圖，**一律不生成 `mermaid` 語法區塊，亦不用 ASCII 字符畫出**，而改以高解析度、清晰易讀的 **PNG 圖檔**呈現，統一存放於專案 `figures/` 目錄下（例如 `figures/10_multi_agent_topologies.png`），並使用標準 Markdown 圖片語法嵌入（如 `![圖 10-1：圖表名稱](figures/10_multi_agent_topologies.png "圖 10-1：簡要說明")`）。
2. **視覺可讀性與頁面比例要求：** PNG 圖表應具備高對比配色、足夠大的中英文字級、充足留白與準確的繁體中文標籤（禁用 Emoji 與裝飾性符號）；版面比例宜適配 A4 PDF 頁面寬度，並於講義樣式中設定 `max-width: 100%; height: auto;`，確保轉出 PDF 後文字清晰可辨且不超出頁面邊界。

---

# 八、表格

表格的用途是整理資訊，而不是取代說明。

建立表格之前，應先介紹：

- 為什麼需要比較？
- 比較哪些面向？

表格之後，再整理：

- 最重要的差異
- 使用情境
- 應如何理解比較結果

不要讓表格孤立存在。

### 表格前後空白行與防溢出規範（重大排版原則）
- **前後保留空白行：** 表格結束後若緊接著一般文字段落、次級標題或清單，兩者之間**必須保留至少一個空白行**；表格開始前若有前導文字，亦應保留一個空白行。否則 Markdown 預覽與 PDF 轉檔引擎（如 VS Code Preview、GitHub、Puppeteer）會將接續文字誤判為表格的最後一列，造成結構破壞。
- **頁面寬度適配（嚴禁超出 PDF 頁寬）：**
  - 控管表格欄位數量，原則上以 **3 至 5 欄**為宜，避免多欄過寬導致字體過度擠壓或破版。
  - 儲存格內應維持簡潔扼要的關鍵陳述，**避免塞入過長的文字段落、整段原文或無空白之長字串**（如長檔案路徑、長 URL 或連續長代碼）。
  - 講義版首 `<style>` 應搭配表格自動換行與寬度上限設定（如 `width: 100%`、`max-width: 100%`、`table-layout: auto`、`word-break: break-word`），確保匯出 PDF 時表格完整落於頁面邊界內。

---

# 九、條列式內容

教材應以完整段落為主。

只有符合下列情況時，才建議使用條列：

- 流程步驟
- 比較項目
- 重點整理
- API 參數
- 檢查清單

不要把整個章節寫成大量條列。

若同一頁有超過三分之一內容都是條列，通常代表文字說明不足。

---

# 十、Markdown 使用原則

教材使用 Markdown 撰寫。

請遵循：

- 使用標準 Heading。
- 使用標準 Code Block。
- 適度使用 Table。
- 保持空白行一致。

不要：

- 混用 HTML。
- 使用任何 Emoji、圖示（Icons）或裝飾性符號（全面禁用）。
- 使用特殊 Markdown Hack。

教材應保持良好的可讀性。

### 禁絕使用圖示（No Icons / Emojis 原則）

1. **教材講義內容全面禁用**：
   - 包含各級標題、段落內文、引言區塊、表格、條列項目與 PNG 圖表內之文字標註，**嚴禁使用任何 Emoji、圖示或裝飾性符號**（如放大鏡、火箭、打勾、叉號、警告三角、燈泡、書籤、彩球、圖釘、手指等任何裝飾符號）。
   - 一律採用純文字與正式書面語標示，以維持大學教材與學術專書的嚴肅性與閱讀品質。
2. **程式範例與終端機輸出全面禁用**：
   - 教材中所展示之程式碼、範例腳本以及專案工具執行時之終端機輸出（`print` 語句、日誌紀錄、狀態提示、錯誤回報），**亦一律禁止包含任何 Emoji 與圖示**。
   - 所有狀態提示請改用具備語意的中英文純文字標籤（例如：`[資訊]`、`[進度]`、`[成功]`、`[警告]`、`[錯誤]`、`[指引]`、`[OA]`、`[封閉]`）。
   - 此規範能徹底杜絕跨平台終端機（如 Windows 預設編碼）下發生 `UnicodeEncodeError` 崩潰，確保程式在各作業系統環境的高度穩定性。

### 程式碼呈現原則（No Full Code Blocks 原則）

為使講義維持簡潔明瞭、易於研讀，**講義中不需呈現完整或龐大的原始程式碼**（例如數十行至數百行之完整 Python 腳本）：
1. **標示存放路徑**：講義只需明確說明該程式在專案工作區中的存放相對路徑（例如 `scripts\fetch_openalex.py` 或 `scripts/fetch_openalex.py`）。
2. **闡明目的與用途**：以清晰段落說明該腳本的存在目的、解決什麼問題、輸入與輸出為何。
3. **提供執行指令範例**：提供學生在終端機操作該程式的具體命令（例如 `python scripts/fetch_openalex.py search "主題關鍵字"`）。
4. **解析關鍵機制與邏輯架構**：以重點摘要、條列或 PNG 圖表說明程式的核心演算法、資料流向或關鍵例外處理，引導學生理解原理，而無需迫使學生在講義中滾動閱讀冗長程式碼。
5. **極簡配置除外**：若為極短設定範例（例如數行之 JSON 配置或環境變數），可精簡呈現。

### PDF 頁面寬度與防溢出排版規範（Page-Width Safety）

教材講義最終會透過 Markdown 預覽或 Puppeteer 匯出為正式 A4 PDF 講義，撰寫時必須嚴格控制文本、表格與程式區塊的視覺寬度，**確保任何元素均不超過 PDF 頁面寬度**：
1. **控制文字段落與行內字串長度**：單一段落應聚焦單一概念，避免寫出動輒上千字、缺乏換段呼吸空間的超長段落；內文與引言區塊中的長檔案路徑、長網址或連續英文參數應適度拆句或換行，避免不可斷行之長字串撐破 PDF 右側邊界。
2. **控制程式敘述、指令與目錄樹寬度**：程式碼區塊（` ``` `）內的單行長度建議控制在 **70 至 80 字元以內**。過長的終端機指令應使用換行續行，目錄樹右側的說明註解亦應精煉（避免把長句直接貼在樹狀圖行尾）；同時在講義版首 `<style>` 保留 `pre`、`code` 與 `blockquote` 的自動換行保護（如 `white-space: pre-wrap;`、`word-break: break-word;`、`overflow-wrap: break-word;`），杜絕右側文字遭裁切。
3. **控制表格與圖片之頁面適配**：表格維持 3 至 5 欄內並精簡儲存格字數，搭配 `width: 100%; max-width: 100%; word-break: break-word;` 樣式；所有視覺圖表改採清晰易讀之 PNG 檔案，並設定 `max-width: 100%; height: auto;`，確保全文件整齊落於安全版心內。

---

# 十一、敘事連續性

章節之間應具有自然的轉承。
不要讓每一節看起來像獨立文章。

例如：

> 前一節介紹了 Context Sources，本節將進一步討論 Context 如何進入模型。

這類過渡文字能協助學生建立整體架構。

---

# 十二、教材深度

教材不應只有「是什麼」。

每一個重要概念，都應回答下列問題：

- 為什麼需要？
- 如何運作？
- 有哪些限制？
- 與其他方法有何不同？
- 實際如何應用？

如果只介紹定義，而沒有背景或應用，通常代表說明仍然不足。

---

# 十三、案例使用

每一章至少應包含一個案例。

案例可以來自：

- Antigravity 2.0 Desktop
- MCP
- AI Agent
- Python
- 課程專案
- 真實工作流程

案例應具有連續性。

不要每個章節都重新建立完全不同的情境。

---

# 十四、結語

每一章最後，都應加入一段簡短的小結。

小結不是重複內容，而是協助學生建立整體觀念。

建議回答：

- 本章最重要的觀念是什麼？
- 與上一章有何關係？
- 下一章將介紹什麼？

讓整本教材具有一致且流暢的閱讀體驗。

---

# 最終目標

完成教材後，請再次確認：

- 是否像一本教材，而不是 ChatGPT 回答。
- 是否以完整段落進行說明。
- 是否具有自然的章節銜接。
- 是否維持正式書面語。
- 是否兼顧概念、原理與案例。
- 是否具有一致的 Markdown 格式。
- 是否已將所有架構與流程圖改以清晰易讀的 PNG 圖片檔案呈現（不含 Mermaid 語法）。
- 是否檢查過長段落、表格欄寬與程式區塊行寬，確保轉出 PDF 後不超出頁面寬度。

如果讀者能夠連續閱讀整個章節，而不覺得內容像一連串零碎回答，便符合本教材的寫作目標。
